# ثبت فروش و پرداخت POS — نسخهٔ 0.4.0

سرویس و API فروش از نسخهٔ 0.2.0 موجود است و در نسخهٔ 0.4.0 رابط صندوق و فاکتور نیز از آن استفاده می‌کنند. تمام درخواست‌ها باید آنلاین، از طریق نشست WordPress با nonce معتبر یا Application Password استاندارد روی HTTPS باشند. نام کاربری یا اطلاعات ورود در درخواست JSON قرار نمی‌گیرد.

## گردش کار

۱. `GET /wp-json/universal-pos/v1/payment-methods` روش‌های دستی فعال را برمی‌گرداند.

۲. `POST /wp-json/universal-pos/v1/sales` سفارش واقعی WooCommerce با وضعیت `pending` ایجاد می‌کند. مبلغ، مالیات، ارز و قیمت‌ها از WooCommerce می‌آیند. موجودی برای پنج دقیقه رزرو می‌شود و هنوز کاهش نمی‌یابد.

۳. مبلغ پاسخ سرور را به صندوق‌دار نشان دهید. پس از دریافت واقعی وجه، درخواست `POST /sales/{id}/payments` را با تأیید صریح دریافت وجه ارسال کنید. سفارش با `payment_complete()` نهایی می‌شود. موجودی فقط از چرخهٔ استاندارد WooCommerce کاهش می‌یابد.

۴. `GET /sales/{id}` برای بررسی نتیجه و دریافت خلاصهٔ سفارش و پرداخت‌هاست. با `POST /sales/{id}/cancel` می‌توان فقط سفارش پرداخت‌نشده را لغو کرد و رزرو آن را آزاد کرد. لغو تکراری بی‌اثر است. فروش پرداخت‌شده از این مسیر لغو نمی‌شود؛ ماژول مرجوعی و بازپرداخت هنوز ساخته نشده است.

تمام مسیرهای فروش به هر دو مجوز `upos_access_pos` و `upos_create_sales` نیاز دارند. صندوق‌دار تنها به فروش خودش دسترسی دارد. مدیر برای دسترسی به فروش دیگران باید `upos_view_orders` و مجوز استاندارد ویرایش همان سفارش را نیز داشته باشد.

## درخواست ایجاد فروش

هدرها: `Content-Type: application/json`، یک `Idempotency-Key` تصادفی و یکتا برای این سبد، و در احراز هویت کوکی هدر `X-WP-Nonce`.

نمونهٔ ساختار درخواست؛ شناسه و مشخصات را با دادهٔ واقعی فروش جایگزین کنید:

```json
{
  "items": [
    {"product_id": 123, "quantity": 2}
  ],
  "billing": {
    "first_name": "نام مشتری",
    "last_name": "نام خانوادگی",
    "phone": "09123456789",
    "email": "",
    "country": "IR"
  },
  "note": ""
}
```

شماره تلفن با تبدیل ارقام فارسی و عربی و حذف فاصله/پرانتز/خط تیره نرمال می‌شود؛ ۷ تا ۱۵ رقم با علامت `+` اختیاری پذیرفته می‌شود. حساب کاربری خودکار ساخته یا به شماره تلفن تطبیق داده نمی‌شود. نام، نام خانوادگی و تلفن الزامی و ایمیل اختیاری است. آدرس می‌تواند شامل `state`، `city`، `postcode`، `address_1` و `address_2` باشد. آدرس برای محاسبهٔ مالیات طبق سیاست WooCommerce به سفارش داده می‌شود؛ هزینهٔ ارسال در فروش حضوری اضافه نمی‌شود.

برای مشتری موجود، `customer_id` را با مجوز `upos_view_customers` بفرستید. مقادیر پیش‌فرض از پروفایل مشتری گرفته و با فیلدهای ارسال‌شده ترکیب می‌شوند؛ پروفایل کاربر تغییر نمی‌کند. معافیت مالیاتی ثبت‌شدهٔ مشتری از WooCommerce خوانده می‌شود.

حداکثر ۱۰۰ ردیف، شناسهٔ محصول بدون تکرار و تعداد صحیح ۱ تا ۱۰۰۰ مجاز است. برای محصول متغیر، شناسهٔ variation مشخص را ارسال کنید. تنوع‌های «هر سایز/هر رنگ» که بعضی گزینه‌هایشان خالی است فعلاً رد می‌شوند. محصول ساده و تنوع با ویژگی‌های مشخص، از جمله تنوع با موجودی مشترک والد، پشتیبانی می‌شوند.

قیمت کالا، مبلغ نهایی و وضعیت سفارش از مشتری پذیرفته نمی‌شوند؛ نیت تخفیف فقط با فیلدهای مستند زیر ارسال می‌شود. پاسخ شامل `id`، `number`، `status`، `paid`، `currency`، `total`، `tax`، `items`، `payments` و `expires_at` به‌صورت UTC است. قیمت محاسبه‌شدهٔ سفارش برای همین مهلت پنج‌دقیقه‌ای تثبیت می‌شود؛ تغییر بعدی قیمت محصول سفارش قبلاً آماده‌شده را خودکار بازقیمت‌گذاری نمی‌کند. برای گرفتن قیمت جدید فروش قبلی را لغو و فروش جدیدی آماده کنید.

## تأیید دریافت وجه

برای نهایی‌سازی، هدر `Idempotency-Key` جدیدی مخصوص همین پرداخت بسازید. `expected_total` باید همان مبلغ آخرین پاسخ سفارش باشد. مثال زیر فقط ساختار پرداخت ترکیبی یک مبلغ فرضی را نشان می‌دهد:

```json
{
  "received": true,
  "expected_total": "100.00",
  "payments": [
    {"method": "cash", "amount": "40.00"},
    {"method": "card_terminal", "amount": "60.00", "reference": "شماره پیگیری واقعی"}
  ]
}
```

روش‌های پایه `cash`، `card_terminal` و `bank_transfer` هستند. برای دو روش غیرنقدی، `reference` الزامی است. هر ردیف می‌تواند `notes` اختیاری داشته باشد. مبلغ‌ها رشتهٔ اعشاری بدون جداکننده و با دقت ارز فروشگاه هستند؛ اعداد منفی، نمای علمی، اعشار اضافه و مبلغ صفر در ردیف پرداخت رد می‌شوند. جمع پرداخت‌ها دقیقاً با مبلغ سرور مقایسه می‌شود، نه با مقایسهٔ اعشاری شناور. تا ۲۰ ردیف و حداکثر ۱۵ رقم در مقدار برحسب کوچک‌ترین واحد ارز پشتیبانی می‌شود. برای سفارش صفرمبلغ، `payments: []` مجاز است و هیچ دریافت مالی ساختگی ثبت نمی‌شود.

`received: true` باید تصمیم آگاهانهٔ صندوق‌دار پس از دریافت وجه باشد. افزونه وجهی از بانک یا دستگاه وصول نمی‌کند و نتیجهٔ دستگاه را شبیه‌سازی نمی‌کند. شماره کارت، CVV، رمز و اطلاعات محرمانهٔ بانکی را به API ارسال نکنید.

تطابق دریافت‌ها با مبلغ شامل مالیاتِ سفارش و موجودی دوباره بررسی می‌شود؛ سپس اجزای دریافت و دفتر مالی در یک تراکنش ذخیره می‌شوند و WooCommerce پرداخت را تکمیل می‌کند. تغییر ارز یا دقت ارز پس از ایجاد فروش، پرداخت را متوقف می‌کند. در صورت تغییر مبلغ خود سفارش نیز باید مبلغ جدید بررسی شود. پرداخت ناقص، وجه اضافه و بازپرداخت از این endpoint پشتیبانی نمی‌شوند.

برای محدودکردن روش‌های دستی، گزینهٔ `upos_manual_payment_methods` در WordPress باید آرایه‌ای از شناسه‌های مجاز بالا باشد. پیش‌فرض هر سه روش است؛ صفحهٔ تنظیمات هنوز ساخته نشده است. این گزینه اطلاعات محرمانه ندارد.

## تکرار، خطا و موجودی همزمان

مسیرهای بازیابی رابط (همگی با همان مجوزهای فروش):

| مسیر | روش | رفتار |
| --- | --- | --- |
| `/products/scan?code=...` | GET | تطبیق دقیق بارکد اختصاصی یا SKU، شامل variation؛ ابهام ۴۰۹ |
| `/sales/recent` | GET | ۱۵ فروش اخیر ساخته‌شده توسط همین کاربر؛ منبع رکورد نگاشت و CRUD واقعی سفارش |
| `/sales/lookup?key=...` | GET | بازیابی نتیجهٔ آماده‌سازی همان کاربر، با همان قفل درخواست |
| `/sales/abandon` | POST | بدنهٔ `{"key":"..."}`؛ اگر سفارشی ثبت شده، همان را برمی‌گرداند؛ وگرنه نشانهٔ انصراف پایدار می‌سازد تا POST دیررس سفارش تازه نسازد |

در رجیستری، انصراف با `order_id=0` و هش مشخص نگهداری می‌شود و در فهرست فروش‌ها ظاهر نمی‌شود. هیچ سبد، مشتری یا سفارش موازی در آن ذخیره نشده است. پاسخ فروش، دقت اعشاری و نماد ارز همان سفارش را هم برمی‌گرداند تا نمایش سابقه پس از تغییر تنظیمات ارز مخدوش نشود.

- کلید درخواست باید ۸ تا ۱۲۸ کاراکتر از حروف لاتین، ارقام و `. _ : -` باشد؛ UUID انتخاب مناسبی است. کلید ایجاد فروش به کاربر محدود است. کلید پرداخت به فروش و کاربر تأییدکننده محدود است.
- پس از قطع ارتباط، ابتدا `GET /sales/{id}` را بررسی کنید و همان درخواست را با **همان کلید و همان بدنه** تکرار کنید. کلید جدید برای تکرار پرداخت نسازید. تکرار موفق همان سفارش و دریافت‌ها را برمی‌گرداند؛ تغییر بدنه با کلید قبلی خطای ۴۰۹ است.
- بعد از پرداخت، کلید دیگری نمی‌تواند وجه جدیدی برای آن فروش ثبت کند. بازپخش پرداخت پس از تغییر بعدی وضعیت سفارش هم پرداخت یا کاهش موجودی دیگری ایجاد نمی‌کند؛ پاسخ وضعیت فعلی سفارش را نشان می‌دهد.
- قفل دیتابیس همزمانی درخواست تکراری و رقابت پرداخت/لغو را کنترل می‌کند. رزرو بومی WooCommerce بین فروش‌های آنلاین و POS مشترک است. POS حتی وقتی backorder برای سایت فعال است، موجودی فیزیکی رزرو‌نشده می‌خواهد.
- انقضا توسط Action Scheduler اجرا می‌شود. اگر runner دیر اجرا شود، endpoint پرداخت همچنان پس از پنج دقیقه درخواست را رد می‌کند. پس از انقضا، سفارش قبلی را لغو و با کلید جدید فروش تازه آماده کنید. هیچ صف فروش آفلاینی ایجاد نمی‌شود.
- خطای اعتبارسنجی ۴۰۰، نبود احراز هویت ۴۰۱، نداشتن مجوز ۴۰۳، فروش ناموجود/غیرمجاز ۴۰۴، تعارض/کمبود موجودی/انقضا ۴۰۹ و خطای زیرساخت ۵۰۳ است. پس از خطای موقت، همان کلید را نگه دارید.
- هر پرداخت شامل زمان UTC، روش، مبلغ، ارز، شناسهٔ سفارش، شناسهٔ کاربر تأییدکننده و شمارهٔ پیگیری است. عملیات آماده‌سازی، دریافت و لغو/انقضا audit می‌شوند. شناسهٔ صندوق‌دار سازنده نیز در متادیتای سفارش باقی می‌ماند.

## مرز تضمین تراکنش

تراکنش InnoDB تغییرات محلی سفارش، موجودی WooCommerce، دریافت‌ها و ثبت‌های اختصاصی را هماهنگ می‌کند. موتورهای غیرتراکنشی و تراکنش تو‌در‌تو پذیرفته نمی‌شوند. ایمیل‌های استاندارد تراکنشی WooCommerce تا پس از commit نگه داشته و در شکست rollback ارسال نمی‌شوند. شکست ارسال ایمیل پس از commit، فروش موفق را به خطای پرداخت تبدیل نمی‌کند. تحویل ایمیل به SMTP تضمین این API نیست.

هوک‌های افزونه‌های ثالث ممکن است وب‌هوک یا اثر خارجی برگشت‌ناپذیر ایجاد کنند، تراکنش را بشکنند یا روش کسر موجودی را تغییر دهند؛ دیتابیس نمی‌تواند این اثرهای خارجی را rollback کند. سازگاری هر اتصال ثالث باید روی سایت آزمایشی بررسی شود. این نسخه فقط گردش فروش و دریافت دستی را پوشش می‌دهد؛ برگشت وجه، اصلاح دفتر مالی پس از refund از ابزارهای دیگر و دفتر عمومی همهٔ تغییرات موجودی هنوز پیاده‌سازی نشده‌اند.

## کوپن و تخفیف دستی

در بدنهٔ ایجاد فروش، `"coupon":"real-code"` یا `"manual_discount":{"type":"amount","value":"10.00","reason":"دلیل تخفیف"}` را اضافه کنید. نوع `percent` نیز با رشتهٔ درصد بیشتر از صفر تا ۱۰۰ و حداکثر دو رقم اعشار پذیرفته می‌شود. مبلغ ثابت با دقت ارز اعتبارسنجی می‌شود و نمی‌تواند از جمع پیش از تخفیف کالا بیشتر باشد. ترکیب این دو فیلد مجاز نیست. دستی به `upos_apply_discounts` نیاز دارد؛ دلیل تا ۲۰۰ نویسه اجباری است.

کوپن واقعی از CRUD و محاسبهٔ بومی WooCommerce می‌آید؛ محدودیت‌های کالا، حداقل خرید، تاریخ و خریدار حفظ می‌شوند. اعتبارسنجی به هویت مشتری سفارش انجام می‌شود، نه حساب صندوق‌دار. سقف مصرف هر مشتری برای مهمان نیازمند ایمیل است. مصرف کوپن هنگام آماده‌سازی در انتظار پرداخت ثبت و در لغو/انقضا آزاد می‌شود؛ پرداخت آن را دوباره افزایش نمی‌دهد. رقابت دو سفارش برای کوپن تک‌مصرف با نوشتن و بازبینی مصرف در تراکنش کنترل می‌شود. تغییر سیاست/انقضای کوپن یا لغو مجوز تخفیف پیش از پرداخت، ثبت وجه را رد می‌کند.

خروجی فروش علاوه بر `discount`، فیلد `coupon` (برای دستی رشتهٔ خالی) و `manual_discount` (بدون دستی `null`) دارد. مقدار و دلیل دستی و عامل در سفارش ثبت می‌شوند؛ جزئیات داخلی فقط در API محافظت‌شده‌اند.

## سبدهای موقت سروری

این مسیرها به مجوزهای ورود صندوق، فروش و مشاهدهٔ موجودی نیاز دارند و فقط دادهٔ همان کاربر را برمی‌گردانند:

| مسیر | روش | رفتار |
| --- | --- | --- |
| `/carts` | GET | حداکثر ۵۰ سبد فعال خود کاربر؛ `key`، `label`، زمان ایجاد/انقضا |
| `/carts/{key}` | POST | ذخیرهٔ اتمی و idempotent سبد با کلید جدید |
| `/carts/{key}` | GET | ادامهٔ سبد؛ انتظار برای پایان ذخیرهٔ در جریان با همان قفل |
| `/carts/{key}` | DELETE | حذف محتوای سبد/مشتری و ثبت نشانگر حذف برای درخواست دیررس |
| `/products/batch` | POST | بدنهٔ `{"ids":[123,456]}`، ۱ تا ۱۰۰ شناسه؛ محصولات قابل‌نمایش با قیمت/موجودی روز و `missing` |

نمونهٔ بدنهٔ ذخیره:

```json
{
  "label": "خرید بعدازظهر",
  "basket": {
    "items": [{"product_id": 123, "quantity": 2}],
    "billing": {"first_name": "", "last_name": "", "phone": ""},
    "coupon": "real-code"
  }
}
```

کلید در URL همان قواعد `Idempotency-Key` را دارد و به کاربر محدود است. ذخیره، اطلاعات ناقص مشتری را می‌پذیرد؛ دادهٔ غیرخالی باید معتبر باشد. `basket` همان ساختار ایجاد فروش بدون قیمت است و هیچ نام/قیمت محصول، سفارش، رزرو موجودی یا دریافت مالی ایجاد نمی‌کند. پاسخ شامل `key`، `label`، `basket` و `expires_at` به UTC است. کلید و بدنهٔ یکسان پاسخ یکسان می‌دهند؛ تغییر بدنه با همان کلید ۴۰۹ است.

برای ذخیرهٔ مجدد سبد ویرایش‌شده، یک کلید تازه و فیلد ریشهٔ `"replaces":"old-key"` بفرستید. ساخت نسخهٔ جدید و پاک‌کردن محتوای قبلی یک تراکنش است. اگر قبلی مصرف، حذف یا منقضی شده باشد کل عملیات رد می‌شود. اعتبار هفت روز است؛ job روزانه محتوای منقضی را پاک می‌کند و API بدون انتظار برای job آن را رد می‌کند. ناشناس/کاربر دیگر سبد را نمی‌بیند؛ کلید ناشناخته ۴۰۴ و سبد حذف/مصرف/منقضی‌شده ۴۰۹ است.

پس از بازخوانی اطلاعات روز، برای تبدیل به فروش `parked_cart_key` را کنار سایر فیلدهای `POST /sales` بفرستید. سبد هنوز قابل ویرایش است؛ همان payload ثابت اجباری نیست. ردیف سبد در تراکنش سفارش قفل و فقط یک بار مصرف می‌شود، حتی با دو کلید فروش متفاوت. شکست رزرو/ثبت سفارش مصرف را rollback می‌کند. پس از موفقیت، محتوای شخصی پاک و تنها شناسهٔ واقعی سفارش حفظ می‌شود؛ لغو بعدی سفارش سبد را دوباره فعال نمی‌کند.

در قطع پاسخ ذخیره، ابتدا GET همان کلید و سپس در صورت لزوم POST همان بدنه و کلید را تکرار کنید. DELETE کلید ناشناخته نیز نشانگر حذف می‌گذارد تا POST دیررس نتواند آن را زنده کند. نشانگرها پس از هفت روز حذف می‌شوند؛ کلید هرگز برای سبد دیگری بازاستفاده نشود. هیچ API ذخیرهٔ آفلاین وجود ندارد.

## بارکد اختصاصی

پیش‌فرض متا `_upos_barcode` است؛ تنظیم استاندارد `upos_barcode_meta_key` فقط کلید سفارشی را می‌پذیرد و از کلیدهای داخلی WooCommerce محافظت می‌کند. تغییر آن مهاجرت داده نیست. فرم استاندارد محصول/تنوع، nonce و مجوز `edit_product` همان محصول را بررسی می‌کند. نوشتن بارکد تکراری یا برخورد با SKU دیگری رد می‌شود؛ واردکردن مستقیم متای مبهم نیز باعث توقف اسکن با ۴۰۹ می‌شود. صفرهای ابتدا حفظ و حداکثر ۶۴ نویسهٔ ASCII از حروف/ارقام و `. _ : + / -` پذیرفته می‌شود.
